### 0.1 规范用语

- **必须**：上线或阶段验收不可缺少的强制要求。
- **应**：默认实现要求，只有经过评审的例外才可调整。
- **可**：产品可以根据客户、渠道或成本策略选择的实现方式。
- **目标态**：18–24 个月周期结束时需要形成的完整能力集合。
- **现有 IDaaS 能力**：仓库中已存在的认证、组织、权限、OIDC、应用管理、审计、租户上下文或适配器能力。

### 0.2 结论摘要

Getbrick Open Platform 是 Getbrick 在 IDaaS 之上建设的开发者与业务能力开放平台。平台将身份、应用、权限、凭证、API、计量、计费、生态、运营和安全能力统一到一个可治理、可审计、可商业化的产品体系中，使企业能够把内部能力安全地开放给内部团队、客户、合作伙伴和生态开发者。

本 PRD 采用以下三项不可妥协的产品原则：

1. **复用优先**：身份认证、会话、组织、RBAC、OIDC、应用/平台/客户端管理、审计脱敏、密钥引用和健康检查优先复用现有 IDaaS 能力，避免建设第二套身份与安全内核。
2. **开放平台域隔离**：新开放平台作为独立限界上下文建设，拥有独立模块、权限、数据表、API、队列、密钥边界、部署单元和运营指标；不直接扩展或依赖现有 IDaaS 控制面的内部表和路由。
3. **合规内生**：中国大陆的数据、实名、隐私、密码、日志、备案、审计、供应商和事件响应要求在产品模型、流程和验收标准中体现，而不是在上线前作为补充检查。

## 1. 愿景与定位

### 1.1 产品愿景

让每一个 Getbrick 客户都能以安全、合规、可计量、可运营的方式，把身份与业务能力转化为可被外部开发者使用的标准产品。

### 1.2 北极星指标

**被成功使用的开放能力月活跃调用租户数**（Monthly Successfully Used API Tenants，MSAT）。

该指标同时要求：租户完成接入、API 被真实业务调用、授权与凭证处于有效状态、调用成功并被正确计量。只有真实使用而非注册数量，才代表开放平台产生了业务价值。

### 1.3 价值主张

| 对象 | 核心价值 | 可感知结果 |
|---|---|---|
| 企业租户 | 将内部身份、组织、权限和业务能力产品化开放 | 缩短开放周期，降低自建网关与计费系统成本 |
| 开发者 | 统一的应用、凭证、授权、文档、调试和运营入口 | 从注册到首次成功调用有明确路径，问题可自助定位 |
| 应用负责人 | 精细管理环境、密钥、权限、配额和生产发布 | 降低凭证泄露、误授权和配置漂移风险 |
| 最终用户 | 清晰、可控、可撤回的授权体验 | 知道哪个应用访问什么数据，并能撤回授权 |
| 平台运营者 | 统一的租户、API、风险、计量、结算和生态运营视图 | 能快速定位异常、处置事件、解释账单并扩展供给 |
| 生态伙伴 | 可发现、可认证、可结算的能力合作网络 | 能以标准方式接入、推广和经营能力 |

### 1.4 产品定位

Getbrick Open Platform 位于 IDaaS 与业务 API 之间，承担以下职责：

- 将身份和组织能力转换为可授权的产品、API、作用域和声明。
- 将应用、凭证、权限、配额和生命周期转换为可治理的开发者体验。
- 将真实调用转换为可核对、可计费、可分账的用量事实。
- 将客户、开发者、服务商和软件伙伴组织成可持续的生态网络。
- 为中国大陆市场提供可备案、可审计、可运营的安全与合规交付。

### 1.5 产品支柱

1. **身份与授权**：以现有 IDaaS 为身份底座，提供 OIDC/OAuth、细粒度 scope、显式 consent、组织和角色上下文。
2. **开发者自助**：应用、凭证、API 目录、文档、沙箱、日志、Webhook、测试和用量在一个控制台完成。
3. **可靠运行**：限流、配额、熔断、审计、密钥轮换、可观测性、发布门禁和事件响应形成闭环。
4. **商业闭环**：计量、计价、配额、账单、发票、伙伴结算和收入分析使用统一事实源。
5. **生态增长**：认证、服务目录、应用市场、联合解决方案、开发者活动和伙伴分润支持供给扩张。
6. **合规可信**：数据目录、隐私请求、留存、跨境、实名与安全事件响应在平台内可证明。

### 1.6 目标态范围原则

目标态范围覆盖租户、开发者、应用、API 产品、凭证、授权、计量计费、生态、运营、合规、安全、开发者体验、SDK、文档、支持、部署形态和商业化运营。路线图中的阶段只表达依赖、风险和验收顺序，不把任何目标态能力定义为永久排除项。

## 2. 背景与问题

### 2.1 现有 Getbrick IDaaS 基线

仓库现有能力已经覆盖开放平台所需的重要安全底座：

| 现有能力 | 当前可复用内容 | 开放平台使用方式 |
|---|---|---|
| 身份认证 | 密码、邮箱验证、短信 OTP、TOTP MFA、会话管理、登录策略 | 复用认证会话与安全策略，开放平台不另建密码数据库 |
| 组织与成员 | 组织、成员、邀请及成员角色 | 将租户组织映射为开放平台组织上下文，成员权限通过适配器读取 |
| RBAC | 角色继承、权限点、通配权限、数据范围、启动期校验 | 复用权限解析和守卫思想，开放平台权限使用独立命名空间 |
| OIDC | RP、OP、Discovery、JWKS、Authorization Code、PKCE、Token、UserInfo、Introspection、Revocation、Logout | 复用 IDaaS OIDC OP/RP 能力承载终端用户授权和单点登录 |
| 应用管理 | 应用、平台渠道、OIDC 客户端及子资源管理 | 通过应用适配器登记和发布开放平台应用，避免复制应用主数据 |
| 平台渠道 | 微信及其他小程序、公众号、开放平台适配器 | 复用平台身份交换和外部身份绑定能力 |
| 生命周期 | active、disabled、archived、purged，readiness、effectiveStatus、version、ETag | 复用安全状态和并发保护，开放平台维护独立发布状态 |
| 凭证 | `secret_ref`、服务端 Secret Resolver、轮换和撤销语义 | 复用 Secret Binding 模式，开放平台新增凭证策略和业务元数据 |
| 审计 | 数据库 hooks、脱敏、审计 sink、事件字段 | 统一事件格式并增加开放平台事件类型，敏感信息沿用脱敏规则 |
| 租户基础 | fixed、dedicated、shared 模式、请求上下文、事务和 RLS 约束 | 作为隔离设计和生产门槛参考，开放平台另建租户数据模型 |
| 控制面 | `/api/idaas/v1` 下的能力、用户、角色、会话、审计和应用管理 | 保持 IDaaS 管理职责；不将其作为开发者产品 API |
| UI 与适配器 | `@getbrick/idaas-ui` 管理原语、NestJS 适配器、共享 contracts | 复用视觉与契约基础，开放平台建设独立控制台信息架构 |

### 2.2 当前问题

1. **从身份能力到可经营 API 的链路断裂**：IDaaS 已能安全管理身份和应用，但开发者仍需自行实现产品目录、凭证发放、授权范围、文档、调试、计量和账单。
2. **应用配置缺少面向生态的发布模型**：现有应用资源关注身份接入与运行状态，尚未表达 API 产品、环境、版本、配额、商业条款、发布审核和生态关系。
3. **凭证管理缺少平台级治理**：单个应用的 secret 引用和轮换机制需要扩展为凭证目录、权限边界、IP 限制、环境隔离、批量轮换和风险联动。
4. **调用与收入事实脱节**：业务调用、限流、失败重试、套餐、账单、分账和税务需要统一事件和可重放计量链路。
5. **开发者运营缺少自助闭环**：注册、实名认证、测试密钥、文档、示例、状态页、问题反馈和发布通知需要形成一致体验。
6. **合规证据分散**：身份审计、网关日志、账单、合作伙伴、数据请求和安全事件需要能够按租户、主体、时间和请求关联。
7. **中国大陆部署形态多样**：公有云、专有云、客户本地化和混合模式需要明确责任边界、数据驻留、升级、应急和可移植性规则。
8. **生态供给缺少信任机制**：开发者和服务商需要认证、评价、版本兼容、质量指标、结算和下架机制，平台需要可治理的市场体系。

### 2.3 产品机会

Getbrick 的差异化机会是把“可嵌入的 IDaaS 内核”延伸到“可运营的开放平台”：保留数据和部署灵活性，同时提供公有云规模化能力、标准 API 体验、生态分发和持续安全更新。开放平台既是客户交付能力，也是 Getbrick 未来的能力分发与收入增长入口。

## 3. 目标、原则与成功标准

### 3.1 产品目标

- 让企业在受控条件下发布身份、组织、权限和业务 API。
- 让开发者在 30 分钟内完成测试凭证创建、首次授权和示例调用，在 24 小时内完成首个生产应用的联调。
- 让平台运营者能够对租户、应用、凭证、调用、账单、风险和生态供给进行统一管理。
- 让每一次敏感操作都有主体、租户、资源、版本、请求和结果的可审计证据。
- 让中国大陆客户能够选择适合自身数据与网络要求的部署方式，并明确服务责任边界。

### 3.2 成功标准

| 维度 | 18 个月运营基线 | 24 个月目标态 |
|---|---:|---:|
| 可接入租户设计容量 | 1,000 | 10,000 以上，按压测结果扩展 |
| 活跃开发者设计容量 | 5,000 | 50,000 以上 |
| 首次成功 API 调用完成率 | ≥ 70% | ≥ 90% |
| 控制台关键任务成功率 | ≥ 99.5% | ≥ 99.9% |
| 管理面月可用性 | ≥ 99.95% | ≥ 99.95% 以上，按套餐分层 |
| 凭证泄露导致的可用凭证暴露 | 0 | 0 |
| 计量与账单差异率 | ≤ 0.5% | ≤ 0.1% |
| 高危安全漏洞未修复时长 | 72 小时内缓解 | 24 小时内缓解，发布级修复形成证据 |
| 开发者支持首次响应 | 1 个工作日内 | 4 小时内或按支持等级 |
| 生态认证伙伴 | 20 家 | 200 家以上 |

### 3.3 设计原则

- **单一事实源**：身份事实归 IDaaS，应用安全状态归现有应用域，开放平台业务事实归开放平台域。
- **默认安全**：显式授权、最小权限、短时凭证、服务端密钥、精确回调地址和可撤销授权为默认路径。
- **隔离优先**：租户、应用、环境、凭证、数据和日志均可单独授权、单独撤销和单独审计。
- **先可解释再自动化**：自动化决策必须有规则、证据、人工接管和申诉路径。
- **契约驱动**：API、事件、SDK 和文档由同一版本化契约生成或校验。
- **渐进增强**：通过阶段门槛交付能力，所有目标态能力在路线图中有明确落点。
- **中国本地化**：时间、币种、税务、发票、实名、网络、语言、数据驻留和供应商适配采用大陆市场语义。

## 4. 现有能力复用与开放平台域隔离

### 4.1 目标逻辑架构

```text
客户/开发者/终端用户
        │
        ▼
开放平台门户与开发者控制台
        │
        ▼
开放平台管理面：租户、开发者、应用目录、API、凭证、授权策略、计量、结算、生态、运营
        │
        ├── 身份与登录适配器 ──► 现有 IDaaS：认证、会话、组织、RBAC、OIDC、应用与平台
        ├── 发布与发布状态投影 ◄── 现有 IDaaS 应用/客户端/平台能力
        ├── 审计与策略适配器 ◄── 现有 IDaaS 审计脱敏与安全事件
        └── 事件与数据同步 ─────► 开放平台事件总线、数据域和运营域

开发者应用/服务端/小程序
        │
        ▼
开放平台 API 网关与数据面：认证、授权、限流、计量、审计、Webhook
        │
        ▼
IDaaS 与业务能力服务
```

### 4.2 复用清单

| 复用域 | 复用内容 | 开放平台责任 |
|---|---|---|
| 登录与会话 | IDaaS 的密码、短信、邮箱、TOTP、会话、锁定和单点登出 | 负责开放平台门户接入、MFA 策略、租户级登录体验和审计关联 |
| 身份主体 | IDaaS user、organization、member、invitation | 只保存主体引用、映射和必要快照，不复制密码、凭证或会话秘密 |
| 权限底座 | IDaaS RBAC 图、权限解析、组织上下文和数据范围 | 使用 `open:` 命名空间建立独立角色与授权策略，完成资源级判定 |
| OIDC | IDaaS OP/RP、Discovery、JWKS、Code+PKCE、UserInfo、Introspection、Revocation、Logout | 定义开放平台 scope、claim、consent、客户端和业务授权记录 |
| 应用与客户端 | 现有 application、platform、client 生命周期、readiness、ETag、外部身份 | 通过同步/适配器投影开放平台发布状态、API 环境和凭证策略 |
| 密钥引用 | `secret_ref`、Secret Binding、轮换、宽限、撤销、Resolver | 管理平台凭证的用途、权限、环境、过期和风险，不把原始密钥写入开放平台表 |
| 审计 | 脱敏 hook、事件 sink、请求上下文、审计字段 | 扩充开放平台事件和业务上下文，保留跨域 request_id、tenant_id、actor_id |
| 租户机制 | fixed、dedicated、shared 的设计原则、请求上下文、事务、RLS | 开放平台域独立建表和仓储；生产共享模式必须有租户解析器、事务和 RLS |
| 控制台基础 | NestJS 适配器、React UI、共享 contracts、分页与错误封装 | 建设开放平台专属页面、权限和 API 契约，不把内部 IDaaS DTO 暴露给客户 |
| 运维基础 | readiness、liveness、迁移、健康检查、审计 sink | 增加业务依赖、数据域、计量管道、事件总线和结算 readiness |

### 4.3 强制隔离规则

1. **限界上下文隔离**：开放平台作为新的业务域，拥有独立的应用服务、仓储、迁移、权限和 API 契约；不把开发者、API 产品、用量或账单表加入现有 IDaaS 控制面。
2. **控制面职责隔离**：现有 `@getbrick/idaas-control-plane` 继续负责 IDaaS 用户、角色、会话、审计及身份应用管理；开放平台控制面负责租户、开发者、产品、凭证、商业和生态。两者可以部署在同一进程，但必须使用不同模块、路由和权限命名空间。
3. **数据访问隔离**：开放平台仓储只能访问 `gb_open_*` 逻辑数据域及经过批准的只读身份适配器；禁止直接查询或更新 `gb_idaas_*` 内部表。跨域同步使用版本化接口、事件或经过评审的只读投影。
4. **API 隔离**：现有 `/api/idaas/v1` 和 OIDC issuer 保持兼容；开放平台新增 `/api/open/v1`、开发者数据面路径和独立版本策略。新接口不复用内部管理 DTO 作为公开契约。
5. **凭证隔离**：开放平台凭证由开放平台密钥服务和 Secret Resolver 管理；身份域的 OIDC 客户端秘密继续由 IDaaS 管理。两者通过用途、主体和引用关联，原始秘密不跨域复制。
6. **权限隔离**：IDaaS `user/admin` 角色不自动等价于开放平台 `platform_admin`；开放平台管理员必须在开放平台域内完成角色授予、职责分离和审计。
7. **故障隔离**：开放平台计费、计量或市场服务故障不能使现有 IDaaS 登录和 OIDC 失效；IDaaS 身份服务不可用时，开放平台进入明确的不可认证状态并停止高风险签发。
8. **发布隔离**：开放平台的数据库迁移、密钥轮换、配置发布和回滚不直接改变现有 IDaaS 的迁移序列；两者在部署编排层进行兼容性和 readiness 检查。
9. **责任隔离**：每个域拥有独立 owner、SLO、告警、事故手册和变更审批；共享组件的变更必须经过双域回归。

### 4.4 现有控制面与开放平台控制面的边界

| 维度 | 现有 IDaaS 控制面 | 新开放平台控制面 |
|---|---|---|
| 管理对象 | IDaaS 用户、角色、组织、会话、审计、身份应用/平台/客户端 | 租户、开发者、开放平台应用、API 产品、凭证、授权策略、用量、账单、伙伴 |
| 主要使用者 | 客户管理员、安全管理员、身份管理员 | 企业租户管理员、开发者、应用负责人、平台运营、财务、生态与合规 |
| 认证来源 | IDaaS 原生会话和 RBAC | 复用 IDaaS 登录，叠加开放平台域角色、MFA 和职责分离 |
| 数据表 | `gb_idaas_*` 及现有应用管理表 | `gb_open_*` 逻辑域及独立投影表 |
| API 根路径 | `/api/idaas/v1`、现有 OIDC 路径 | `/api/open/v1`、独立数据面路径 |
| 事实归属 | 身份与应用安全事实 | 开放平台产品、商业、计量和生态事实 |
| 审计事件 | 现有 IDaaS 事件体系 | 开放平台事件体系，保留关联 ID |
| 运维指标 | 身份服务、会话、OIDC、应用可用性 | 租户接入、API 成功、授权、计量、账单、生态与 DX 指标 |

## 5. 用户角色与权限

### 5.1 用户角色

| 角色 | 所属范围 | 主要目标 | 典型权限 |
|---|---|---|---|
| 平台超级管理员 | 平台 | 平台级配置、租户治理、应急处置 | `open:platform:*`，需双人审批 |
| 平台运营员 | 平台 | 租户、应用、API、公告、工单日常运营 | `open:tenant:manage`、`open:application:review` |
| 平台审核员 | 平台 | 开发者、租户、应用和生态资质审核 | `open:verification:review`、`open:listing:review` |
| 平台安全员 | 平台 | 风险、凭证、事件、漏洞和应急响应 | `open:security:*`、`open:credential:revoke` |
| 平台财务员 | 平台 | 计价、账单、发票、结算和收入核对 | `open:billing:*`、`open:settlement:*` |
| 平台合规员 | 平台 | 隐私请求、留存、审计、跨境与监管配合 | `open:compliance:*` |
| 租户所有者 | 租户 | 租户整体责任与商业决策 | `open:tenant:owner` |
| 租户管理员 | 租户 | 成员、应用、凭证、配额和账单管理 | `open:tenant:admin` |
| 开发者组织管理员 | 开发者组织 | 开发者成员、项目和密钥管理 | `open:developer:org:manage` |
| 开发者 | 开发者组织 | 创建应用、调试 API、管理个人凭证 | `open:application:write`、`open:api:test` |
| 应用负责人 | 应用 | 应用配置、版本、发布和生产凭证 | `open:application:manage`、`open:credential:write` |
| 安全审核人 | 租户/应用 | 审核高风险权限和生产发布 | `open:application:security-review` |
| 财务联系人 | 租户 | 查看账单、发票和付款状态 | `open:billing:read`、`open:invoice:manage` |
| 审计员 | 租户/平台 | 查询不可变审计记录和合规证据 | `open:audit:read` |
| 支持人员 | 平台/租户 | 查看脱敏上下文并处理工单 | `open:support:case` |
| 生态伙伴管理员 | 伙伴 | 管理伙伴成员、能力、结算和资质 | `open:partner:manage` |
| 终端用户 | 授权关系 | 登录、查看授权应用、同意或撤回权限 | `open:user:consent` |

### 5.2 权限设计

- 权限采用 `open:<资源>:<动作>[:<范围>]` 形式，资源至少包括 `tenant`、`developer`、`application`、`api-product`、`credential`、`authorization`、`usage`、`billing`、`partner`、`audit`、`compliance`。
- 租户角色和平台角色分开授权；平台超级管理员不被默认视为任何租户的业务所有者。
- 读取、写入、验证、发布、禁用、归档、清除、轮换、撤销、导出、结算和查看个人信息等高风险动作分离。
- 生产凭证签发、应用发布、权限提升、租户主体变更、账单调整、数据导出和清除必须支持双人复核或二人审批，具体由策略配置。
- 资源权限由角色授权、资源归属、租户边界、环境、状态、配额和风险条件共同决定；仅通过前端隐藏按钮不构成授权。
- 所有权限变更必须记录变更前后摘要、操作者、审批者、租户、资源版本、request_id、时间和结果。
- 终端用户授权与开发者控制台 RBAC 分离：控制台权限决定“谁可以管理”，用户 consent 决定“应用能访问什么”。

### 5.3 关键职责分离

| 冲突场景 | 必须分离的角色 |
|---|---|
| 创建并独自发布生产应用 | 应用开发者与应用安全审核人 |
| 生成并下载生产凭证 | 应用负责人与租户管理员/安全审核人 |
| 修改计量单价 | 平台产品/财务配置人与结算复核人 |
| 审核租户实名材料 | 审核员与租户所有者 |
| 处理密钥泄露 | 安全员与凭证管理员 |
| 导出或清除个人数据 | 合规审核人与执行人 |
| 处理账单争议 | 财务客服与结算复核人 |
| 伙伴上架与下架 | 生态运营与合规审核人 |

## 6. 领域模型

### 6.1 领域边界

| 限界上下文 | 负责内容 | 关键事实 |
|---|---|---|
| 租户上下文 | 企业主体、租户生命周期、成员、合同、区域与数据策略 | `tenant_id` 是开放平台资源的强制归属 |
| 开发者上下文 | 开发者主体、组织、认证等级、联系方式、协议、收款信息 | 开发者可以属于多个租户，但每次操作有明确主体 |
| 应用上下文 | 应用、环境、版本、发布、回调、隐私与渠道映射 | 应用安全状态可投影自 IDaaS，发布状态归开放平台 |
| API 产品上下文 | 产品、资源、操作、版本、schema、SLA、配额和定价引用 | API 目录是运行时授权与计量的共同依据 |
| 凭证上下文 | API key、OAuth client、服务账号、签名密钥、mTLS、Webhook secret | 只保存引用、指纹、版本、状态和使用限制 |
| 授权上下文 | 用户授权、应用授权、scope、claim、策略、consent、撤销 | 授权对象必须绑定租户、应用、客户端、主体和策略版本 |
| 计量计费上下文 | 用量事件、聚合、配额、费率、账单、发票、结算和对账 | 用量事件不可变，账单由可重放聚合生成 |
| 生态上下文 | 伙伴、供给、目录、上架、评价、认证、分润和结算关系 | 伙伴不能绕过平台质量与合规门禁 |
| 运营上下文 | 公告、状态、事件、工单、风险、功能开关、发布 | 运营动作与租户业务动作均可审计 |
| 合规安全上下文 | 数据目录、同意、隐私请求、留存、风险、漏洞、供应商和证据 | 合规策略可阻断发布、调用和数据处理 |

### 6.2 核心实体

| 实体 | 关键字段 | 所有者 | 备注 |
|---|---|---|---|
| Tenant | `tenant_id`、主体类型、主体名称、统一社会信用代码或身份证明引用、区域、套餐、状态、策略版本 | 平台/租户 | 统一社会信用代码等敏感材料使用加密存储或外部 KYC 引用 |

| ApiVersion | 版本、兼容性、发布状态、弃用时间、变更日志 | 产品 | 版本发布与应用绑定关系可追踪 |
| ApiOperation | 方法、路径、操作 ID、scope、请求/响应 schema、错误、成本单位 | 产品 | 运行时网关和文档的唯一契约 |

| ApiKeyProfile | key 引用、权限、配额、速率限制、最后使用时间 | 应用/平台 | 通过 key_id 关联 Secret Binding |

| UsageAggregate | 周期、维度、量、金额、版本、状态 | 计量/财务 | 可由事件重算并保留差异 |

| Partner | 主体、类型、资质、状态、联系人、合同、结算账户 | 生态 | 结算账户信息与身份主体分离 |

| FeatureFlag | 开关、环境、租户、版本、审计、灰度规则 | 平台 | 高风险操作默认关闭并需审批 |

### 6.3 关系与约束

- 一个租户可以拥有多个开发者组织、应用、产品引用、账单账户和 API 凭证。
- 一个开发者组织可以参与多个租户，但每个应用、凭证、授权和用量事件必须有明确租户。
- 一个应用可拥有多个环境和客户端；生产环境与沙箱环境的凭证、权限、配额、回调和数据存储相互隔离。
- 一个 API 产品可以有多个版本和操作；应用绑定具体版本或兼容范围，不能使用未发布版本。
- 一个凭证只属于一个主体（应用、服务账号或伙伴）和一个环境；跨环境复制必须重新授权并产生新指纹。
- 一个用户授权至少绑定租户、应用、客户端、scope 集合、claim 集合、策略版本和有效期。
- 一条计量事件必须具有全局唯一 `event_id` 或业务幂等键，重复提交只产生一次计费影响。
- 已结算账单、已签发审计证据和已生效价格版本不可原地覆盖，修正通过冲正或追加调整记录完成。
- `purged` 资源不得继续签发凭证、接受调用或产生新授权；清除任务必须经过保留期和合规审批。

### 6.4 标识、命名与数据分级

- 租户、应用、产品、凭证和计量事件使用不可预测的公开 ID；内部主键与外部 ID 分离。
- 公开 API 采用版本化资源名；内部枚举可扩展，但公开字段变更需遵循兼容规则。
- 建议逻辑表前缀为 `gb_open_`，名称、字段、索引和迁移由开放平台独立维护。
- 数据分为公开、内部、敏感个人信息、重要数据、凭证秘密和安全审计六级；每级有最小权限、留存、加密和导出策略。
- 个人信息、实名材料、支付信息、凭证秘密和重要数据分别使用独立存储、密钥和访问审批。

### 7.2 导航与体验原则

- 新用户从“快速开始”进入，而不是先面对复杂配置表单。
- 控制台采用“租户上下文 → 应用 → 环境 → 凭证/API”的层级组织。
- 生产环境使用明显的环境标识、风险提示和二次确认。
- 所有列表提供搜索、筛选、状态、更新时间、责任人和分页；敏感字段默认掩码。
- 页面必须同时展示当前身份、当前租户、当前环境和有效权限，避免跨租户误操作。
- 错误提示同时给出稳定错误码、可执行动作、request_id 和文档链接；内部堆栈不面向普通用户。
- 所有高风险操作提供预览影响范围、审批人、预计生效时间和回滚方式。
- 桌面端优先保证复杂表格和权限配置效率，移动端保证审批、告警、密钥撤销和工单处理能力。

## 9. 核心流程与状态机

### 9.1 租户开通与认证流程

1. 用户通过 IDaaS 完成登录、MFA 和必要的邮箱/手机号验证。
2. 用户创建租户，选择主体类型、区域、套餐、联系人和数据策略。
3. 系统生成租户 ID、默认角色、默认策略、账单账户和隔离命名空间，并写入审计事件。
4. 用户或平台运营员提交企业/个人认证材料、协议和授权证明。
5. 平台执行格式、重复主体、风险、黑名单、人工审核和合规策略校验。
6. 审核通过后租户进入运营中，初始化计量、通知、密钥、事件和默认配额。
7. 任一关键材料过期、主体变化或风险升高时，平台进入复核或暂停状态，并通知责任人。

**验收标准**：同一主体重复申请可识别；审核动作、证据和状态迁移完整；租户 ID 在所有下游资源中保持一致；租户隔离测试覆盖数据库、缓存、队列、对象存储、日志和密钥。

### 9.2 开发者接入流程

```text
注册 → 资料完善 → 协议接受 → 认证提交 → 自动校验 → 人工/规则审核
  → 认证通过 → 创建/加入开发者组织 → 创建应用 → 创建沙箱凭证
  → 首次授权 → 首次成功调用 → 生产审核
```

- 注册和登录由 IDaaS 负责；开放平台记录开发者域状态。
- 认证材料不足时返回字段级问题、补充入口和期望完成时间。
- 生产发布前必须完成应用信息、权限、隐私、回调、凭证策略和 API 兼容性检查。
- 认证状态、协议版本、风险分数和审核意见对用户可见，敏感材料只显示掩码。

### 9.3 应用创建与生产发布流程

1. 开发者选择租户和开发者组织，创建应用及环境。
2. 系统调用 IDaaS 应用适配器创建或关联身份应用；平台不复制密码、会话和原始客户端秘密。
3. 配置应用类型、回调、权限、产品、版本、配额、Webhook、隐私和运行环境。
4. 在沙箱完成认证、授权、调用、错误处理、限流、Webhook 和重试验证。
5. 提交生产发布包，系统执行 schema、权限、回调、凭证、依赖、隐私和计费检查。
6. 安全审核人确认高风险项，发布服务生成版本、ETag、发布记录和回滚点。
7. 生产发布后观察成功率、延迟、错误率、授权量和计量差异；触发回滚时撤销受影响版本并通知调用方。

**状态机**

```text
草稿 → 配置中 → 校验中 → 待审核 → 已批准 → 沙箱可用 → 生产可用
  │       │         │          │          │          │
  └───────┴─────────┴──────────┴──────────┴──────────┴→ 禁用
                                                            ↓
                                      归档 → 清除（满足保留与审批条件）
```

现有 IDaaS 的 `active`、`disabled`、`archived`、`purged`、`readiness` 和 `effectiveStatus` 继续作为安全事实；开放平台发布状态独立记录，运行时取两者交集。

### 9.4 凭证签发、轮换与撤销流程

1. 有权限的负责人选择应用、环境、凭证类型和最小 scope。
2. 系统校验应用状态、发布状态、租户策略、IP 限制、风险和配额。
3. 密钥服务生成或解析凭证，数据库只保存引用、指纹、版本和用途。
4. 原始凭证在一次性响应中返回；浏览器不持久化敏感值，通知和日志只显示指纹。
5. 轮换时创建新版本，按策略设置生效时间、宽限期、旧版本撤销时间和回滚点。
6. 灰度验证通过后撤销旧版本；撤销通过缓存失效、队列清理、网关配置和会话撤销传播。
7. 发生泄露时，安全员可立即撤销全部相关凭证并触发风险事件、应用禁用和通知。

**凭证状态机**

```text
待生成 → 生成中 → 有效 → 轮换中 → 待撤销 → 已撤销
                         │          │
                         └→ 已过期  └→ 撤销失败 → 重试/人工处置
```

**验收标准**：并发轮换最多一个有效主版本；宽限期内可追踪调用；撤销后无缓存旧凭证继续成功；原始 secret 在数据库、审计、日志、错误、导出和通知中均不存在。

### 9.5 终端用户委托授权流程

```text
授权请求 → 客户端与回调校验 → IDaaS 认证 → 组织/风险上下文
  → Consent 展示 → 用户同意/拒绝 → 授权记录 → 授权码 → Token
  → API 调用 → 计量与审计 → 刷新/撤销/到期
```

1. 客户端提交精确 redirect_uri、state、nonce、PKCE、scope、claim 和 audience。
2. IDaaS 验证 issuer、签名算法、回调、state、会话、用户状态和组织上下文。
3. 需要交互时展示应用用途、字段、权限、留存和撤回方式；`prompt=none` 缺少认证或 consent 时返回标准协议错误。
4. 用户同意后记录精确 scope、claim、策略版本、用户手势、时间和应用版本。
5. 授权码一次性消费，Token 短时有效；刷新、注销、撤销和重放检测均记录审计。
6. 用户可在授权中心查看应用、权限、最近使用和撤回入口。
7. 应用被禁用、凭证撤销、租户暂停或风险策略触发时，数据面立即停止新的高风险调用。

### 9.6 API 调用、授权、限流与计量流程

1. 网关接收请求并解析租户、应用、客户端、凭证、request_id、trace_id 和区域。
2. 校验 TLS、客户端认证、凭证状态、租户状态、应用状态、环境、scope、claim、策略和回调绑定。
3. 查询配额、速率限制、预算、风险和黑白名单；失败时返回稳定错误码、建议重试时间和 request_id。
4. 将请求路由到 IDaaS 适配器或业务 API；响应进行 schema 校验、敏感字段过滤和错误归一化。
5. 写入不可变用量事件；事件包含业务幂等键，计量管道异步聚合，不因计费短暂故障丢失调用事实。
6. 返回标准响应头：request_id、trace_id、rate_limit、quota、billing_period 和兼容版本信息。
7. 失败调用按产品规则标记是否计费；重试、去重、超时和异步完成遵循统一幂等语义。

### 9.7 计量到账单流程

```text
调用事实 → 校验与去重 → 周期聚合 → 定价计算 → 配额/预算检查
  → 账单草稿 → 对账 → 开票/收款 → 结算 → 争议/调整 → 完成
```

- 每个周期先锁定生效价格、合同、折扣、税率和时区版本。
- 聚合结果可由原始事件重算；迟到事件进入调整或下期，规则提前告知租户。
- 账单生成前执行租户、应用、产品、伙伴和内部一致性检查。
- 账单发布后产生不可变快照；退款、补收、争议和红字调整使用关联记录。
- 租户可查看用量明细、账单构成、价格版本、发票状态和争议进度。

#### 9.7.1 发票争议审核与裁决

争议的提出、审核与裁决是三个独立写入口，各自有独立权限、幂等键、审计动作和领域事件；`update` 权限不能推进审核或裁决。

| 阶段 | 状态迁移 | 权限动作 | 审计动作 | 领域事件 |
|---|---|---|---|---|
| 发起争议 | 账单进入争议；争议为「已提出」 | `invoice.update` | `invoice.update` | `commerce_dispute.created` |
| 开始审核 | 已提出 → 审核中 | `invoice.dispute.review` | `invoice.dispute.review` | `commerce_dispute.status_changed` |
| 裁决 | 审核中（或已提出）→ 已接受 / 已驳回 | `invoice.dispute.decide` | `invoice.dispute.decide` | `commerce_dispute.decided` |
| 撤回 | 已提出 / 审核中 → 已撤回 | `invoice.dispute.withdraw` | `invoice.dispute.withdraw` | `commerce_dispute.status_changed` |

- 终态（已接受、已驳回、已撤回）不可再迁移；重复裁决返回状态迁移冲突，不覆盖既有裁决。
- 裁决必须给出裁决依据（引用）和可选裁决说明；说明与争议理由同口径上限 500 字符、禁止控制字符，并禁止承载凭证或银行账号等高敏信息。
- 裁决人只记录主体标识，不记录姓名、邮箱或电话；争议原因、裁决依据和裁决说明都不写入审计与事件负载，审计只记录裁决结果、原状态、目标状态、争议与账单标识以及说明长度。
- 裁决采用版本乐观并发：读取争议版本后按版本写入，版本不匹配即冲突，重复请求按幂等键重放且不重复产生事件。
- 争议终态不自动改写账单状态；账单回到待支付、开票中、完成或作废仍走账单自身的状态迁移与审计。

### 9.8 生态伙伴上架与结算流程

1. 伙伴提交主体、合同、数据处理协议、能力和结算资料。
2. 平台执行认证、资质、数据、安全、SLA、财务和反商业贿赂审核。
3. 伙伴创建产品草稿、版本、文档、沙箱、价格和测试用例。
4. 平台进行接口、安全、隐私、商业、兼容性和持续质量审核。
5. 上架后目录展示版本、标签、评分、SLA 和商业条款；变更触发重新评估。
6. 用量事件按伙伴归属聚合，结算单经复核后生成付款或应收记录。
7. 质量、投诉、漏洞或违规达到阈值时进入整改、降级、下架或终止流程，历史账单和审计保留。

### 9.9 隐私请求与数据主体生命周期

1. 用户通过控制台或专用渠道提交访问、更正、删除、撤回或注销请求。
2. 系统完成身份核验、租户确认、请求范围确认和风险检查。
3. 合规人员按数据目录查找相关身份、应用、授权、日志、账单和伙伴数据。
4. 执行访问、纠正、删除、匿名化或限制处理；法定留存、争议和安全证据按策略保留。
5. 结果通过安全渠道通知用户，记录处理期限、实际动作、失败原因和人工复核。
6. 关闭账号或撤回授权时，联动 IDaaS 会话、开放平台凭证、缓存、队列和 Webhook。

### 9.10 安全事件与凭证泄露处置

```text
发现 → 分级 → 遏制 → 凭证/会话撤销 → 影响评估 → 通知与监管配合
  → 修复 → 灰度恢复 → 复盘 → 行动项关闭
```

- 事件负责人可一键定位受影响租户、应用、凭证、版本、区域和请求。
- 撤销、冻结、限流、禁用和回滚均有审批、幂等和回执。
- 对外通知包含影响范围、时间、已采取措施、下一更新时间、支持渠道和复盘入口。
- 复盘输出根因、影响、检测缺口、修复、预防、负责人和截止日期。

### 12.3 数据面 API 约定

- 数据面 API 以产品、版本和 operation_id 为稳定识别，不以页面路由或内部服务名称作为契约。
- 读取请求可使用应用凭证或用户访问令牌；写入请求按产品要求使用幂等键、签名、租户上下文和版本字段。
- API 网关在请求进入业务服务前完成认证和粗粒度授权，业务服务仍执行资源级授权，不能只依赖网关。
- 失败响应采用统一 envelope：错误码、用户可读消息、request_id、可重试标记、字段问题和文档引用。
- 统一返回 request_id、trace_id、rate_limit、quota、billing_period、api_version 和 deprecation 信息。
- 数据面不允许返回内部堆栈、数据库错误、provider token、session_key、client secret、secret_ref 或其他租户信息。

### 12.4 标准错误、分页和并发

**统一错误结构**

| 字段 | 说明 |
|---|---|
| `error.code` | 稳定机器码，例如 `invalid_scope`、`credential_revoked`、`tenant_suspended`、`rate_limit_exceeded` |
| `error.message` | 面向调用方的安全、可执行描述 |
| `error.request_id` | 用于日志、链路和支持定位的请求标识 |
| `error.retryable` | 是否适合重试 |
| `error.retry_after` | 建议重试时间或秒数 |
| `error.details` | 字段级校验问题或安全可披露的限制信息 |
| `error.documentation` | 对应文档和版本入口 |

- 列表统一采用游标分页，默认 20，最大 100；返回 `items`、`next_cursor`、`has_more` 和可选 `total`。
- 写操作支持 `Idempotency-Key`；资源更新支持 `If-Match`/ETag，版本冲突返回 `CONFLICT`。
- 所有写入响应返回 `request_id`；敏感写操作返回审计引用而非内部对象。
- 时间统一使用 ISO 8601，存储采用明确时区；业务账期使用租户约定和中国标准时间默认值。

### 12.5 Webhook 事件模型

Webhook 事件至少包含：

| 字段 | 说明 |
|---|---|
| `event_id` | 全局唯一事件 ID，用于去重 |
| `event_type` | 版本化事件类型 |
| `occurred_at` | 事件发生时间 |
| `tenant_id` | 租户标识 |
| `actor` | 触发主体或系统标识 |
| `resource` | 资源类型、ID、版本和状态 |
| `data` | 最小必要业务数据 |
| `schema_version` | 事件契约版本 |
| `signature` | 使用 Webhook secret 计算的签名和时间戳 |
| `request_id` | 关联请求 |
| `trace_id` | 关联链路 |

- Webhook 至少一次投递，消费者通过 `event_id` 幂等；平台提供指数退避、最大重试、死信和重放。
- 签名验证必须包含原始请求体、时间戳和 secret version，防止重放。
- 事件 payload 采用数据最小化，不发送密码、Token、client secret、session key、完整实名材料或敏感个人信息。
- 消费者可按事件类型订阅，平台提供 schema、示例、测试事件、版本变更和弃用窗口。

## 13. 事件模型

### 13.1 事件信封

所有内部事件和对外 Webhook 使用统一信封，内部事件额外包含 `source_domain`、`correlation_id`、`causation_id`、`trace_id` 和 `schema_registry_version`。事件名称采用过去式或事实式，事件类型不可复用旧语义。

### 13.2 事件目录

| 事件类别 | 事件示例 | 生产者 | 主要消费者 | 可靠性要求 |
|---|---|---|---|---|
| 租户 | `tenant.created`、`tenant.review_submitted`、`tenant.activated`、`tenant.suspended`、`tenant.closed` | 租户域 | 身份适配器、计量、通知、合规、运营 | 至少一次、租户有序 |
| 开发者 | `developer.registered`、`developer.verification_updated`、`developer.risk_changed` | 开发者域 | 风控、生态、通知、运营 | 至少一次、可重放 |
| 应用 | `application.created`、`application.mapping_synced`、`application.release_submitted`、`application.released`、`application.disabled` | 应用域 | IDaaS 投影、网关、计量、审核、通知 | 至少一次、资源版本有序 |
| API | `api_version.published`、`api_version.deprecated`、`api_version.retired`、`api_operation.changed` | API 产品域 | 网关、SDK、文档、配额、计费 | 至少一次、发布锁 |

| 调用 | `api.call.accepted`、`api.call.rejected`、`api.call.completed`、`api.call.failed`、`api.call.rate_limited` | 网关/业务服务 | 计量、风险、账单、观测 | 至少一次、幂等键 |
| 计量 | `usage.event_accepted`、`usage.event_rejected`、`usage.aggregate_closed`、`usage.reconciliation_required` | 计量域 | 账单、财务、运营、租户 | 至少一次、可重算 |

### 13.3 事件处理规则

- 事件消费者必须使用 `event_id`、业务幂等键和 schema_version 做去重与兼容。
- 事件按资源 ID 或聚合键保持局部有序；跨资源全局顺序不作为业务前提。
- 生产者只发布已提交的领域事实；状态变化和业务事实由同一事务或可靠 outbox 机制衔接。
- 事件 schema 只能向后兼容地增加可选字段；删除、改名、改变语义或收紧枚举需要新版本和迁移窗口。
- 消费者失败进入重试、死信、人工重放和告警；重放必须保留原始 event_id 并生成新的投递尝试记录。
- 事件总线、队列和对象存储按租户分区、分级加密、访问审计和留存策略管理。

### 14.2 可靠性与灾备

- 共享管理面目标 RPO ≤ 15 分钟、RTO ≤ 60 分钟；专属部署按合同配置更高等级。
- 关键配置、凭证元数据、授权、计量和账务具备跨可用区备份与定期恢复演练。
- 数据库迁移、消息队列、缓存、对象存储和密钥服务均支持版本化、灰度、回滚和 readiness 检查。
- 每日备份、跨区域复制、恢复抽检、故障演练和供应商故障切换必须有记录。
- 计量和账务数据支持从事件和快照重放；恢复后执行幂等重放和差异对账。
- 生产启动必须通过身份、应用、网关、事件、密钥、数据库和通知依赖的健康检查。

### 14.3 安全指标

- 生产环境全链路使用 TLS；敏感内部通信使用双向认证或等效网络隔离。
- 原始凭证只存在于密钥服务/受控签发响应，普通数据库、日志、指标、错误、审计和导出中为零。
- 关键安全回归用例覆盖认证绕过、租户越权、scope 扩大、重放、回调篡改、CSRF、SSRF、注入、批量枚举和限流绕过。
- 高危漏洞在约定 SLA 内完成缓解、修复、回归和客户通知；中危漏洞有明确修复计划。
- 每季度完成威胁建模、权限复核、密钥轮换抽查、依赖审计和渗透测试；高风险变更需双人批准。
- 关键管理员、财务、审核和清除权限启用 MFA、短会话、IP/设备风险和异常登录保护。

### 14.4 数据与隐私指标

- 100% 关键数据资产登记用途、分类、主体、区域、留存、删除和负责人。
- 100% 个人信息处理活动具备合法性基础、告知/同意或合同依据和可验证证据。
- 100% 跨境数据流完成法律机制、接收方、范围、风险和合同评估。
- 删除任务成功率 ≥ 99.9%，失败任务有告警、重试、人工处置和结果证明。
- 日志、指标、追踪和支持视图的敏感字段泄露事件为 0；抽样审计覆盖率达到 100% 高风险字段。
- 隐私请求在适用法定期限内完成，超期任务自动升级并形成管理报告。

### 14.5 兼容性、可维护性与成本

- 兼容 Node.js 20/22/24、TypeScript、NestJS、PostgreSQL 16 和现有 Getbrick 迁移约定；版本矩阵在发布文档中维护。
- 数据库 schema、API schema、事件 schema、SDK 和文档均采用语义版本和弃用策略。
- 核心模块单元测试覆盖率目标 ≥ 90%；安全关键路径、权限边界和计量逻辑要求分支覆盖与集成测试。
- 每次发布生成变更日志、迁移说明、回滚说明、依赖清单/SBOM 和兼容性报告。
- 单位租户、单位调用和单位存储成本可观测；优化不能降低隔离、审计和备份等级。
- 共享组件升级必须完成 IDaaS 与开放平台双域回归、兼容矩阵更新和客户通知。

### 15.2 网络安全与等级保护

- 按系统边界、数据重要性和行业要求完成网络安全等级保护定级、备案、测评、整改和复测。
- 开放平台管理面、数据面、事件总线、密钥、数据库、对象存储、备份、监控和支持系统均纳入资产、边界、访问和审计清单。
- 生产环境采用最小开放端口、网络分区、出站白名单、WAF、 DDoS 防护、管理面隔离和特权访问控制。
- 漏洞扫描、渗透测试、基线核查、配置核查、备份恢复和应急演练形成周期性证据。
- 发生网络安全事件时，按影响分级完成隔离、遏制、取证、报告、通知、恢复和复盘。

### 15.3 个人信息与敏感个人信息

- 以个人信息保护法为核心，建立处理目的、方式、范围、保存期限、个人权利响应和第三方提供规则。
- 只收集完成身份、租户、授权、计量、计费和支持所必需的数据；可选字段默认关闭并说明影响。
- 实名材料、身份证件、手机号、邮箱、设备、IP、位置、行为和生物识别等按敏感程度分级，分别取得适用的告知、同意或其他合法基础。
- 对敏感个人信息执行单独同意或合同依据、最小权限、加密、脱敏、访问审批、留存和删除策略。
- 禁止把个人身份数据、授权 Token、凭证秘密和 provider session_key 放入前端埋点、错误消息、SDK 默认日志或伙伴事件。
- 个人信息主体可查询、更正、复制、删除、撤回同意、注销账号和撤回授权；处理结果可解释、可通知、可证明。
- 未成年人、弱势群体、委托处理、联合营销和自动化决策场景使用专项策略和人工复核。

### 15.4 数据安全与分类分级

- 依据数据内容、影响和业务场景建立公开、内部、敏感个人信息、重要数据和凭证秘密分类。
- 对每类数据定义存储、传输、访问、备份、导出、共享、销毁、跨境和审计策略。
- 重要数据和高风险个人信息使用专用密钥、访问审批、双人复核、异常访问告警和更高留存保护。
- 账号、凭证、支付、实名、审计和业务数据使用不同密钥和权限边界；密钥轮换不影响正在使用的宽限版本。
- 共享模式必须验证租户解析、请求级事务、RLS、缓存键、队列分区、对象存储路径、日志查询和备份恢复的隔离。
- 数据导出采用加密、脱敏、水印、有效期、单次下载或受控传输，并记录导出目的、范围和操作者。

### 15.5 数据跨境与本地化

- 默认将中国大陆租户的个人信息、重要数据和凭证数据存储在经批准的中国大陆地域；具体区域和备份区域可由租户策略选择。
- 任何跨境传输、远程运维访问、全球 SDK 遥测、伙伴处理和境外灾备都必须先完成数据分类、目的、范围、接收方、法律机制、风险评估和合同审查。
- 跨境机制根据适用要求选择安全评估、标准合同、认证或其他合法路径，并保存证据、有效期和续期状态。
- 跨境开关与租户区域、供应商位置、事件路由和日志目的地联动；策略不满足时阻断数据流并给出可解释原因。
- 跨境请求由合规人员审核，开发者可见数据区域和处理方信息。

### 15.6 密码、认证与安全通信

- 按适用法律、国家密码标准和商用密码要求评估算法、密钥管理、签名、证书和加密方案。
- 生产环境使用 HTTPS、强密钥、可轮换签名密钥、稳定 cookie key、精确 issuer 和受控 JWKS。
- OIDC 客户端使用 Authorization Code + S256 PKCE，ID Token 校验、state、nonce、aud、iss、azp、exp 和 redirect URI 均不可绕过。
- API 网关支持 mTLS、private_key_jwt 或受控客户端认证；客户端 secret 不进入浏览器和移动端。
- 凭据、支付、实名材料和重要数据在传输和静态存储时加密；密钥由密钥管理服务和最小权限角色管理。
- 日志、告警、状态页、伙伴目录和错误响应不泄露密钥、Token、个人信息和内部拓扑。

### 15.7 实名、反欺诈与内容/服务治理

- 根据业务类型和监管要求确定租户、开发者、应用、服务商和支付主体的实名/企业认证流程。
- 采用手机号、邮箱、设备、行为、IP、调用模式、关联主体和黑名单进行反欺诈；对高风险行为增加人工审核和申诉。
- 对目录、应用名称、Logo、描述、文档、评论、公告和伙伴素材建立内容审核、投诉、侵权、下架和复审机制。
- 对 API 能力、生成内容、用户上传内容或第三方内容按实际业务建立安全检测、举报、处置和证据留存流程。
- 账号被盗、异常登录、批量调用、滥用和侵权均能关联到主体、租户、应用和事件，并提供冻结与恢复流程。

### 15.8 供应商与第三方

- 维护云、短信、邮件、支付、开票、实名、监控、日志、客服、对象存储、KYC、内容安全和 SDK 分发供应商清单。
- 每个供应商登记处理数据类型、目的、区域、分包方、保留期、安全措施、合同、SLA、退出和替代方案。
- 供应商变更、跨境处理、子处理者和数据泄露进入风险评审与审批；租户可查看适用的第三方说明。
- 关键供应商提供灾备、通知、取证、删除、返还数据和合同终止支持。
- 伙伴访问租户数据前必须完成资质、数据处理协议、权限最小化和审计配置。

### 15.9 合规运营与证据

- 合规中心维护数据目录、同意版本、隐私请求、留存任务、跨境评估、供应商、监管沟通、审计和整改项。
- 每个控制项有 owner、证据位置、频率、阈值、例外审批和复核日期。
- 监管或客户请求可按主体、租户、时间、事件和产品导出最小必要证据包。
- 重大政策、隐私、API 合同、计费和目录变更需经过法务、隐私、安全、产品和财务评审。
- 合规策略异常时可暂停应用发布、数据调用、伙伴上架、账单结算或数据导出，并保留人工恢复流程。

- 开发者认证、合作伙伴认证和技术支持人员使用分级知识库，避免依赖个人经验。
- 每次重大事件、重复故障和高频问题形成根因分析、文档改进、产品缺陷或培训行动项。

### 17.3 网络、可用区与灾备

- 中国大陆生产部署至少划分管理面、数据面、异步任务、密钥、数据库、对象存储、监控和备份的网络边界。
- 共享服务使用租户级配额和公平调度；专属/本地部署提供独立资源、证书、密钥、日志和升级通道。
- 跨域同步采用 mTLS、签名事件、请求级租户上下文、重放保护和断点续传。
- 生产、预生产和沙箱使用不同域名、数据库、密钥、凭证、通知和数据存储。
- 灾备演练至少覆盖数据库恢复、密钥恢复、事件重放、计量对账、凭证撤销、证书轮换和区域切换。
- 客户本地化交付包含安装、配置、迁移、备份、恢复、升级、回滚、验收、运行手册和培训材料。

### 17.4 兼容性与可移植性

- 对外 API、事件、Webhook 和业务数据提供稳定 schema 与版本化迁移工具。
- 客户可导出租户、应用元数据、产品绑定、授权、用量、账单、审计和配置；导出包含字段说明、编码、校验和完整性清单。
- 专属/本地部署可选择平台托管计费、客户账务或混合结算，账务事实和调用事实保持可核对。
- 共享数据库、专属数据库和客户本地数据库使用同一领域模型和迁移检查，降低迁移成本。
- 版本升级提供兼容矩阵、预检查、灰度、回滚和至少一个明确的安全支持窗口。

## 18. 18–24 个月路线图

### 18.1 交付原则

- 路线图覆盖目标态全集；每个阶段有依赖、产出、量化验收和进入下一阶段的门槛。
- 0–18 个月形成可运营、可计费、可审计的开放平台基线；18–24 个月完成规模化、生态成熟、企业部署和持续经营能力。

### 19.3 埋点、口径与治理

- 每个产品、API、租户、应用、环境、区域、伙伴、渠道和版本都必须进入统一维度模型；禁止把个人信息作为分析维度。
- 事件采用统一 event_id、request_id、trace_id、tenant_id、application_id、operation_id 和 occurred_at；时间统一存储，展示按租户时区转换。
- 指标定义、计算 SQL、维度、数据源、刷新时间、负责人和变更记录进入指标目录；同一指标只保留一个权威口径。
- 业务指标与安全指标分离存储和权限；安全事件、凭证和隐私数据只向授权角色展示聚合结果。
- 指标采集支持数据质量校验、延迟、乱序、重复、缺失、异常波动和版本兼容；异常数据先标记再补算。
- 运营报表支持按租户、产品、版本、区域、伙伴和时间下钻，导出遵循数据最小化和审计规则。
- 目标值每个季度复核；客户合同、套餐和合规要求变化时同步更新指标定义和告警阈值。

## 21. 关键假设与前置条件

### 21.1 产品与市场假设

1. 目标客户以中国大陆企业、开发者团队、软件服务商、集成商和平台型客户为主，实际细分行业由首批试点验证。
2. Getbrick 已具备可持续维护的 IDaaS 代码、测试、迁移和发布能力，开放平台不需要重建认证和权限内核。
3. 现有 `@getbrick/idaas-control-plane` 的定位保持为 IDaaS 管理边界，开放平台以新限界上下文建设；二者可共享部署基础设施，但不共享业务表和权限。
4. Getbrick 或其运营主体能够在中国大陆提供合法的云服务、备案、合同、支付、开票、客服和事件响应能力；具体主体与资质在 P0 冻结。
5. 首批 API 以身份、组织、权限、应用和渠道能力为主，后续业务能力通过同一产品、授权、计量和生态模型接入。
6. 开发者愿意采用 OAuth/OIDC、API key、private_key_jwt、mTLS 和 Webhook 等标准集成方式；低门槛模板和 SDK 负责降低接入成本。
7. 计量和账务采用事件事实与可重放聚合，接受初期一定的基础设施和财务运营投入。
8. 生态伙伴愿意接受认证、合同、质量、结算和下架治理，目录价值随供给和租户使用形成网络效应。
9. 目标容量、可用性、灾备和支持等级需要在客户试点、合同和压测后冻结；本文数值作为规划基线。
10. 跨境、境外远程运维、全球 SDK 遥测和海外伙伴处理均以逐项合规评估为前提，不作为默认数据路径。

### 21.2 技术与组织前置条件

- IDaaS 生产环境具备 HTTPS、稳定密钥、持久化 OIDC adapter、数据库会话、Secret Resolver、审计 sink、readiness 和迁移流程。
- 现有应用、平台、客户端、外部身份和微信等适配器有稳定契约，可通过适配器和事件向开放平台投影。
- 平台配备独立的产品、架构、研发、测试、安全、运维、DX、运营、财务、法务、隐私、生态和客户成功 owner。
- 云、KMS/HSM、数据库、消息、对象存储、监控、备份、KYC、支付、开票、短信、邮件和内容安全供应商完成选型和合同评审。
- 组织建立安全漏洞响应、事件值班、隐私请求、账单争议、伙伴审核和客户升级流程。
- 所有阶段验收都需要可重复的测试数据、自动化测试、压测环境、故障注入环境、审计证据和发布回滚方案。

### 21.3 需要在 P0 关闭的假设

- 运营主体、合同主体、品牌/域名、备案和许可路径。
- 首批客户、试点租户、典型业务 API、产品目录和商业模式。
- 共享 SaaS、专属云、客户本地化和混合部署的销售与交付优先级。
- 账期、价格、税费、发票、支付、退款、伙伴分润和合同价规则。
- 数据区域、备份区域、跨境策略、KYC 供应商和隐私请求时限。
- IDaaS 对外契约稳定窗口、上游依赖升级策略和双域回归资源。
- 首批 SDK、文档语言、API 认证方式和兼容标准。
- 事件总线、计量、账单、目录和搜索的技术选型与容量基线。

## 22. 发布验收与运营准备

### 22.1 功能验收

- 租户、开发者、应用、环境、API 产品、凭证、授权、用量、账单、伙伴、运营和合规流程均有可执行主路径。
- 控制台页面与 API 权限矩阵一致；列表、详情、写入、审批、撤销、导出、归档和清除行为与本 PRD 一致。
- 现有 IDaaS 登录、组织、RBAC、OIDC、应用/平台/客户端和审计能力通过开放平台集成验收。
- 沙箱、生产、专属和本地形态的差异通过配置、部署和数据验收，不出现未记录的隐式行为。
- 端到端用户旅程覆盖首次接入、授权、生产发布、计量、账单、支持和退出。

### 22.2 安全验收

- 威胁模型、权限矩阵、数据流图、密钥清单、依赖清单、SBOM、渗透测试和高危修复证据齐全。
- 租户越权、认证绕过、scope 扩大、重放、CSRF、回调篡改、注入、SSRF、批量枚举、限流绕过和敏感信息泄露测试通过。
- 原始凭证、Token、session_key、secret_ref、个人信息和 provider 响应不进入普通日志、指标、前端存储和错误详情。
- 备份恢复、密钥轮换、撤销传播、事件重放、跨区切换、供应商故障和安全事件演练通过。
- 生产发布、清除、导出、权限提升、价格修改、伙伴上架和账单调整具备审批与回滚。

### 22.3 合规验收

- 运营主体、备案/许可、数据角色、隐私政策、服务协议、数据目录和供应商清单完成法务/合规签署。
- 中国大陆租户的数据、备份、遥测、日志、事件和远程运维路径符合已批准的区域策略。
- 敏感个人信息、实名材料、支付信息、重要数据、凭证秘密和审计数据完成分类分级、加密、留存和删除策略。
- 隐私访问、更正、删除、撤回、注销、留存任务、跨境评估、事件通知和监管配合流程完成演练。
- 等级保护、漏洞、渗透、备份、应急、供应链和审计证据可供客户与监管核验。

### 22.4 商业与生态验收

- 价格模型、计量单位、免费/试用/合同规则、最低消费、超额、折扣、税费、发票、支付、退款和争议流程可执行。
- 用量、账单、发票和伙伴结算可以从事件、聚合、价格版本和合同快照重算。
- 伙伴入驻、资质、数据处理、目录上架、API 质量、SLA、投诉、下架和分润流程有完整证据。
- 生态目录、应用市场、开发者认证、课程、活动、案例和反馈机制可以持续运营。
- 客户成功、售前、支持、状态页、公告、知识库和升级机制已准备。

### 22.5 上线后稳定期

- 上线前 30 天建立每日发布、错误、用量、账单、风险、工单和客户健康评审。
- 发生高风险事件时可一键暂停新签发、撤销凭证、禁用应用、隔离租户、关闭目录或冻结结算。
- 每周复盘接入漏斗、首次调用、API 质量、权限拒绝、限流、计量完整性和支持工单。
- 每月复盘 MSAT、留存、收入、单位成本、伙伴质量、合规请求和安全事件。
- 每季度进行容量、灾备、权限、密钥、供应商、隐私、漏洞和灾备演练，并更新风险与路线图。

| 环境 | 应用的 sandbox、staging、production 等运行与凭证隔离单元 |
| API 产品 | 对外提供的一组业务能力、版本、操作、权限、SLA 和商业规则 |
| API 版本 | API 产品的一组兼容 schema、文档、运行规则和生命周期状态 |
| 凭证 | 用于认证、签名、Webhook 或服务间调用的密钥类资源 |
| scope | 授权请求中声明的粗粒度权限集合 |
| claim | Token 中携带并经过策略批准的细粒度身份、组织或资源声明 |
| consent | 终端用户对应用、用途、scope、claim 和数据范围的明确授权决定 |
| 计量事件 | 一次调用或业务动作产生的不可变用量事实 |
| 配额 | 对调用速率、总量、预算或资源使用量的限制 |
| 生态伙伴 | 通过认证并向平台或租户提供能力、方案或服务的组织 |
| 目录 | 面向用户展示 API、应用、SDK、方案和伙伴能力的检索与治理面 |
| 数据面 | 面向开发者实际调用 API 的运行时服务层 |
| 管理面 | 面向租户、运营、审核和生态伙伴的配置与治理服务层 |
| IDaaS | Getbrick 现有身份与访问管理能力，包括认证、组织、RBAC、OIDC、应用和审计 |
| 开放平台域 | 本文定义的新限界上下文，独立承载开发者、产品、凭证、计量、计费、生态和运营事实 |

## 25. 结论

Getbrick Open Platform 的核心交付不是一组孤立的 API 管理页面，而是以现有 IDaaS 为身份安全底座、以独立开放平台域承载开发者产品全生命周期、以中国大陆合规和安全为上线门禁的完整平台能力。18 个月形成可运营、可计费、可审计的基线，24 个月完成规模化、企业部署和生态成熟；所有目标态能力通过阶段、依赖、门槛和验收标准管理交付顺序。
